# Android TV Apps Helper v0.3.0 UX Hardening Design

Date: 2026-09-15  
Status: Approved by the user in conversation on 2026-09-15
Target release: `v0.3.0`

## 1. Goal

Upgrade Android TV Apps Helper from a prompt-led workflow into a deterministic, cross-platform interaction harness for Claude Desktop/Code, Codex, Tencent WorkBuddy, and Doubao Work.

The release must keep every user decision bounded, put verified context inside the active question surface, separate all download and device-mutation approvals, provide device-specific guidance where evidence exists, and report outcomes in concise tables.

## 2. Requirement coverage

| Requirement | Design response |
| --- | --- |
| UX-001 | Question context is structured data and must render inside the active component or equivalent contiguous text block. |
| UX-002 | Internal immutable plan IDs are separated from deterministic user-facing plan names. |
| UX-003 | Task labels come from a fixed copy registry. |
| UX-004 | Recommended apps use selection, download confirmation, verification, and install approval as separate states. |
| UX-005 | Emotn UI flows through default-launcher choice, wallpaper choice, upload, confirmation, and on-site verification. |
| UX-006 | Every new Skill invocation checks the official stable release and persists a 24-hour decline snooze where the host permits it. |
| UX-007 | Safe limited precheck runs automatically before the first business question. |
| UX-008 | Finish choices are concise and non-overlapping. |
| UX-009 | Every interactive reply and final report presents key results in a table with deterministic status symbols. |
| UX-010 | Every finish path reaches device-specific ADB and developer-mode shutdown guidance. |
| UX-011 | Wallpaper and Home-key changes pass separate device compatibility risk gates before plan approval. |
| UX-012 | Dangbei Market resolves from its publisher's official stable download path instead of asking ordinary users for a local APK. |

The detailed observations and acceptance criteria remain in [`docs/ux-feedback-log.md`](../../ux-feedback-log.md). This specification resolves overlaps and defines one implementation contract.

## 3. Chosen architecture

Use one Python core for state, validation, copy, evidence, and structured presentation data. Platform adapters may change only the rendering transport.

The alternatives are rejected:

- Prompt-only enforcement cannot reliably prevent model wording drift, missing context, false success symbols, or skipped approvals.
- Separate platform workflows would duplicate state logic and allow feature parity to drift.

The core produces a complete `InteractionFrame`; the host adapter renders it as a native card, native table and controls, or an equivalent Markdown block.

```text
Core state machine
  ├── session and question lock
  ├── fixed copy registry
  ├── evidence and summary rows
  ├── precheck and update state
  ├── app/download/install plans
  ├── device guide registry
  └── compatibility registry
          ↓
InteractionFrame
  ├── WorkBuddy adapter
  ├── Doubao Work adapter
  ├── Codex adapter
  └── Claude adapter
```

## 4. Session and interaction data

### 4.1 Session schema

Increment the session schema from 2 to 3. Preserve existing fields and add:

- `workflow_revision`
- `session_sequence`
- `interaction_capabilities`
- `update_check`
- `precheck`
- `device_identity`
- `device_guide_match`
- `compatibility_matches`
- `selected_apps`
- `download_confirmation`
- `wallpaper_asset`
- `evidence_records`
- `summary_rows`
- `finish_safety`

Schema-2 sessions migrate without executing commands. Existing `target_serial` and approved-plan data are retained, but an approved plan must be revalidated against the current serial, APK digest, command, risk, and workflow revision before reuse.

### 4.2 Question model

Extend `Question` with:

- `previous_result_summary`
- `progress_summary`
- `blocker_summary`
- `remediation_guidance`
- `evidence`
- `summary_rows`
- `visual_aid`
- `accepted_attachment`
- `display_name`

Every persisted question remains required and retains its stable `question_id`, state, options, answer contract, and attempt count.

An invalid, missing, ambiguous, stale, or malformed answer increments the attempt count and re-renders the same question. It cannot clear the pending question, advance state, start a download, or run an ADB command.

### 4.3 InteractionFrame

The core renders each reply in this fixed order:

1. A three-to-six-row key status table.
2. A concise blocker or risk statement.
3. Actionable guidance relevant to the current question.
4. Exactly one question.
5. Fixed options and the accepted answer format.
6. Optional technical details after the primary interaction.

For a native modal or card, items 1–5 belong inside the component when supported. If the component accepts only a prompt string, the adapter serializes the table and context into that prompt. If the host cannot render a table inside its component, it renders the table immediately before the component in the same reply and repeats the single most important blocker inside the component. The platform validation report must record this degradation.

## 5. Deterministic presentation

### 5.1 Status symbols

| Symbol | Core status | Meaning |
| --- | --- | --- |
| ✅ | `completed` | The row's stated criterion has verified evidence. |
| ❌ | `failed` | The action was attempted and remains incomplete after allowed recovery. |
| ⚠️ | `attention` | Partial result, compatibility risk, or user verification required. |
| ⏳ | `pending` | Planned or waiting, but not attempted. |
| ⏭️ | `skipped` | Explicitly skipped, unavailable, or not applicable. |

The model never selects a symbol. The core maps execution and evidence records to status. A failed first attempt followed by success is `completed` with “重试后完成”. A device not found by passive discovery is `attention`, not `failed`.

Evidence remains layered:

- `file_validated`
- `installed`
- `launched`
- `runtime_signal`
- `on_site_accepted`

A row can be ✅ only for the evidence level it actually reached. “现场使用正常” requires user-confirmed picture, sound, and remote control.

### 5.2 Fixed copy registry

User-facing labels are loaded from a versioned copy registry. Models may fill verified values but cannot create synonyms.

Required mappings include:

| Internal action | User-facing label |
| --- | --- |
| `launcher_setup` | 设置电视默认桌面 |
| `recommended_apps` | 查看并选择推荐应用 |
| `finish_keep` | 结束本次任务，保留当前桌面和壁纸 |
| `continue_tasks` | 继续其他电视操作 |
| `restore_session_start_launcher` | 恢复本次会话开始时的桌面后结束 |

### 5.3 Plan names

The immutable internal ID remains `PLAN-<digest>`. It continues to bind target serial, APK digest, command, action, and risk.

The user-facing name is generated only by the core:

```text
方案 {two-digit session sequence}：{fixed action label}
```

Example: `方案 01：安装应用`.

IP addresses, ADB serials, package names, and digest fragments do not appear in the main plan title. They remain available in technical details.

## 6. Startup flow

### 6.1 Safe recovery priority

On entry, detect interrupted device mutation or required recovery first. Recovery takes precedence over version checking and precheck. No Skill update can start while device write recovery is incomplete.

### 6.2 Version check

At the first safe point of every new Skill invocation:

1. Fetch a machine-readable stable-release manifest only from `HXWfromDJTU/android-tv-apps-helper` GitHub Releases.
2. Compare versions with strict SemVer.
3. Ignore prereleases on the default channel.
4. If current is latest, continue.
5. If the check fails, record failure and continue with the installed version without claiming it is current.
6. If a newer version exists and its snooze has not expired, show `UPDATE-Q1` before any business question.

The fixed update choices are:

- 更新后继续（推荐）
- 暂不更新并继续，24 小时内不再提醒
- 查看完整更新说明
- 安全退出

Declining persists `declined_version`, `declined_at`, and `snooze_until`. The state is keyed by user, platform, Skill, and target version. Hosts without reliable cross-session persistence are marked incompatible with the 24-hour guarantee rather than repeatedly prompting.

Updates are never silent. The platform package must match the host, SHA-256, Skill ID, and version before installation. Completion requires the host's actual installed-version evidence.

### 6.3 Automatic limited precheck

Remove the old “是否开始只读预检” question. Run these safe read-only checks automatically:

- local execution and LAN capability;
- ADB availability and version;
- `adb devices -l` states;
- active network interface and local address;
- Wi-Fi name when safely accessible;
- existing neighbor cache, known ADB targets, and passive mDNS/service discovery.

The automatic phase must not scan the whole subnet, probe every IP, or connect to an unselected address. Active scanning requires a separate question showing subnet, ports, purpose, and scope.

The first business question includes a result table and asks only whether the computer and TV use the same Wi-Fi. The next question separately asks whether ADB or network debugging is enabled.

No discovery result may call a device a TV without sufficient evidence. Use “可能是电视” when identification is uncertain. Zero passive results do not prove that ADB is disabled.

## 7. ADB guidance

Every no-device, unauthorized, or repeated-discovery question includes concise steps inside the interaction surface:

1. Confirm the computer and TV use the same trusted LAN.
2. Open Settings and enter System, Device Preferences, or About.
3. Select Build or version approximately seven times to enable developer options.
4. Open Developer Options and enable ADB, network debugging, or wireless debugging.
5. Read the TV IP address.
6. Accept the RSA prompt when the Agent connects.

The project will include a public, versioned text guide and an original generic diagram. Device-specific images or links require a verified model/system match and source. An unrelated vendor screenshot may never be presented as the user's TV.

## 8. Task selection and application flow

### 8.1 Task menu

After target lock and inventory, use fixed task names. Selecting a task does not itself mutate the TV.

### 8.2 App list

The app list contains stable index, name, version, installed state, intended action, and availability.

Current distribution policy remains authoritative:

- Clash Meta resolves only from the official MetaCubeX GitHub Release.
- SmartTube may resolve from this project's verified release asset.
- Dangbei Market uses `official_direct` after its official APK identity has been validated; it is downloaded from the publisher's official page/CDN and is not mirrored by this project without redistribution permission.
- `pending_rights` and `pending_file` entries remain visible but disabled and expose no download URL.

An app already at the catalog version is disabled as “已是最新版本”. A zero-executable selection never produces an execution confirmation; it returns a concise result and offers selection changes or another task.

### 8.3 Selection and confirmation

Use a native multi-select component when available. Otherwise accept numbers separated by Chinese enumeration commas, Chinese commas, English commas, or whitespace. The displayed example is always `1、2、3、4`.

Unknown, duplicate, disabled, or malformed choices re-render the same selection question with a precise error and no side effect.

After selection, resolve indices to names and versions and show an independent download confirmation. Only after confirmation may the Skill download and verify files. Installing those files requires a separate immutable install plan and execution approval.

### 8.4 Dangbei Market official resolver

The verified source metadata as of 2026-09-15 is:

- product page: `https://www.dangbei.com/`;
- stable version shown by the publisher: `6.0.7`;
- update date shown by the publisher: `2026-07-06`;
- download target linked by the publisher: `https://app.qingyingyong.net/down/20260706/dangbeimarket_6.0.7_613_znds.apk`;
- publisher-provided backup entry: `https://apk.znds.com/`.

The current execution environment received HTTP 567 from the direct target and did not obtain the APK. Therefore the release cannot mark the item executable until an actual file is obtained and its ZIP structure, manifest, package, versionName, versionCode, minimum SDK, ABI, signing-certificate digest, byte size, and SHA-256 are recorded.

Add catalog distribution mode `official_direct`. It stores the publisher page, resolved version, resolved download URL, allowed redirect hosts, file identity, verification timestamp, and recheck policy. Runtime resolution fetches only the fixed publisher page; it never performs open web search. A redirect to an unlisted host, package/signature mismatch, or changed unverified release fails closed and requests project-maintainer review.

The ordinary user flow never asks the user to source Dangbei Market manually. If the official CDN is unavailable, the options are retry the official source, open the official publisher page, skip temporarily, or exit. An authorized local APK remains an advanced recovery path, not the default solution.

The APK is not uploaded to this project's GitHub Release without explicit redistribution permission. Linking to a publisher-provided download does not establish third-party mirroring rights.

## 9. Default launcher and wallpaper flow

When Emotn UI is already installed or supplied through an authorized and validated source:

1. Verify installation and launch.
2. Ask whether to set Emotn UI as the default launcher.
3. Apply only after explicit approval; preserve the factory launcher package and data.
4. Ask whether to upload one custom image or use the default wallpaper.
5. If custom is selected, require one valid image and a separate apply confirmation.
6. Apply and report command evidence separately from on-site visual acceptance.

Every wallpaper question repeats this fixed meaning inside the component: custom wallpaper may be reset by the vendor system after several days, reboot, system update, or launcher update, and the Skill cannot guarantee permanence.

A missing, failed, or invalid upload does not imply consent to use the default wallpaper. The pending upload question remains until the user explicitly uploads a valid image, selects the default, goes back, or exits.

## 10. Compatibility risk gate

Wallpaper replacement and Home-key default routing are separate compatibility dimensions.

Maintain a versioned registry keyed by manufacturer, model, Android version, SDK, build ID, identified firmware family, current launcher, and action. Each record contains:

- `verified_supported`, `high_risk`, or `unknown`;
- verification count and date;
- evidence summary;
- known failure mode;
- recovery guidance;
- evidence source.

Before either action reaches plan approval, show a table containing the verified TV identity and each selected action's independent risk.

- `verified_supported`: explain that success has been verified but persistence is not guaranteed.
- `high_risk`: use the fixed warning that the current model/system is likely to reject or later reverse the change.
- `unknown`: state that reliable compatibility evidence is unavailable and the action may fail; do not invent a probability.

The reported “小米 Harmony OS 2.0” observation is not used as a registry key. Implementation uses the actual device fingerprint and a normalized, verified system name to avoid confusing HarmonyOS with HyperOS.

Risk acknowledgement is not execution approval. The user may choose both actions, wallpaper only, Home-key only, or cancel. Each choice creates a different plan.

No compatibility fallback may root, flash, factory-reset, clear data, uninstall or disable the factory launcher, or continuously rewrite wallpaper in the background.

## 11. Verification and final report

Every result is table-first. The primary final table includes status, item, result, and evidence. A second small table may show recovered process errors. Raw commands, serials, full package names, stdout/stderr, and logs belong in technical details.

The final task choice is limited to:

- 结束本次任务，保留当前桌面和壁纸
- 继续其他电视操作
- 恢复本次会话开始时的桌面后结束

Restoring the session-start launcher requires a separate plan and approval. The recorded HOME is not described as factory/OEM without separate identity evidence.

## 12. Mandatory safety finish

Every finish path, including a cancelled restore, reaches `FINISH-SAFETY-Q1` after all ADB-dependent work and artifact saving.

While still connected, capture manufacturer, model, Android version, SDK, build, firmware family when reliable, current launcher, and readable developer-setting states. Match a versioned shutdown guide in this order:

1. exact model and system version;
2. model family;
3. vendor system;
4. generic Android TV.

Each guide records the remote-control path to disable ADB/network/wireless debugging and the developer-options master switch. It also records when the model has no master switch, its source, verification date, and optional labeled diagram.

The component shows the ADB and developer-mode status table, friendly TV identity, concise matching instructions, and one question:

- 两项都已关闭
- 找不到设置，查看本型号详细指引
- 暂时保持开启并结束

The default is user-performed shutdown. The Agent does not silently disable developer mode remotely. User confirmation is recorded separately from ADB reachability. A disconnected device alone does not prove that ADB was disabled. If the user says it is closed but new ADB commands still succeed, re-render the same question with that conflicting evidence.

Choosing to keep settings enabled is allowed after a clear LAN-access risk warning, but the final report remains ⚠️ and cannot say the safety finish completed.

## 13. Platform parity

All packages contain identical core code, copy registry, catalog, guides, compatibility data, and test fixtures.

| Platform | Preferred surface | Required fallback |
| --- | --- | --- |
| Codex | Native required choice when available | Markdown table plus numbered menu |
| WorkBuddy | Native required card and multi-select when supported | Markdown table and fixed numbered input |
| Doubao Work | Native local-computer interaction when supported | Markdown table and fixed numbered input |
| Claude Desktop/Code | Native question control when available | Markdown table plus numbered menu |

Host capability detection determines rendering only. It cannot merge questions, infer consent, delete failure rows, alter labels, or change state transitions.

## 14. Error handling

- Network/version check failure: continue on the installed Skill and label the check as unavailable.
- No local execution: stop before ADB and guide the user to a local-computer context.
- ADB missing: show install or path repair choices.
- Device not found: show actual checks, retry count, ADB guide, IP submission, bounded scan choice, or exit.
- Unauthorized/offline: preserve target scope and resolve without killing a shared ADB server when other devices are active.
- Download/hash/platform mismatch: preserve the installed Skill or APK state and stop that item.
- Dangbei official source unavailable: report the official source failure and offer retry, official-page opening, temporary skip, or exit; never fall back to an unknown mirror.
- App rights unavailable: disable selection and expose no URL.
- Launcher/wallpaper incompatibility: show risk before plan approval and preserve the factory launcher.
- Mutation failure: one predefined safe retry at most, then mark ❌ and provide recovery.
- Host UI failure: preserve the same pending question and fall back to text rendering.

## 15. Test design

### 15.1 Unit tests

- Schema-2 to schema-3 migration.
- Context fields survive persistence and invalid-answer retries.
- Stable copy and user-facing plan-name generation.
- Summary status and emoji mapping from evidence.
- Multi-choice parsing for supported separators and invalid/disabled items.
- `official_direct` host allowlist, redirect rejection, package/signature identity, and changed-release failure behavior.
- Update SemVer, prerelease exclusion, fake-clock 24-hour snooze, and manifest validation.
- Precheck classification and active-scan authorization boundary.
- Compatibility matching precedence and per-action risk.
- Wallpaper upload presence and confirmation lock.
- Mandatory finish-safety routing and conflicting ADB evidence.

### 15.2 Contract and snapshot tests

For each platform, render fixtures covering:

- startup with and without update;
- automatic precheck success, partial failure, and cloud-only failure;
- no device on first and repeated attempts;
- native multi-select and text fallback;
- high-risk, verified, and unknown compatibility;
- successful, failed, recovered, pending, and skipped result rows;
- final report and shutdown guidance;
- invalid, stale, missing, and malformed answers.

The same fixture must produce equal question IDs, option values, state transitions, summary meanings, and evidence labels across platforms.

### 15.3 Live validation

Run install-to-dialogue validation on Codex, WorkBuddy, and Doubao Work:

1. install the platform package;
2. verify the host-visible installed version;
3. explicitly invoke the Skill;
4. verify update and automatic precheck entry;
5. verify context/table rendering inside or adjacent to the native component;
6. submit an invalid answer and prove the state does not advance;
7. verify app selection and named download confirmation without performing an unapproved TV mutation;
8. verify finish-safety guidance rendering.

Claude live validation remains deferred. Its package, extracted core, contract fixtures, and deterministic rendering must still pass.

Physical-TV claims remain separate. Package and dialogue tests do not prove wallpaper, Home-key, picture, sound, or remote acceptance on a real TV.

## 17. Release gates

Publish `v0.3.0` only when all applicable gates pass:

| Gate | Required evidence |
| --- | --- |
| Core tests | All unit and contract tests pass from a clean worktree. |
| Skill/plugin validation | Validators pass for source and extracted platform packages. |
| Deterministic builds | Repeated builds produce identical ZIP hashes. |
| Rights and provenance | No unauthorized APK enters Git history or release assets; Clash remains upstream-only. |
| Dangbei source | Publisher version and URL are rechecked; the APK identity passes package, signature, size, and SHA-256 validation, or the item remains non-executable with no user-sourcing requirement. |
| Cross-platform package parity | Shared core, copy, guides, catalog, and compatibility hashes match. |
| Codex live validation | Installed version and required dialogue scenarios observed. |
| WorkBuddy live validation | Chat installation, installed version, and required dialogue scenarios observed. |
| Doubao Work live validation | Local-computer installation and required dialogue scenarios observed. |
| Claude scope | Automated package/contract evidence passes; live validation explicitly remains not run. |
| Public release | Release page and every asset are downloadable without authentication and match published SHA-256 values. |

Failures remain failures or blockers. Automated tests do not substitute for host rendering evidence, and host rendering does not substitute for physical-TV acceptance.
