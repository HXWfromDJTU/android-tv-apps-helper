## UX-001：问题组件内缺少上一轮结果、进度和解决指引

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 补充日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮用户提交的两张 WorkBuddy 截图。截图未作为仓库资源持久化。

### 观察到的问题

在设备发现阶段，WorkBuddy 展示了以下交互：

1. `S2-Q1` 首次未发现设备时，直接询问“接下来怎么做”，提供“重新扫描设备 / 提交电视 IP 地址 / 安全退出”。
2. `S2-Q1` 第三次仍未发现设备时，直接提供“扫描局域网查找电视 / 提交电视 IP 地址 / 再次扫描设备 / 安全退出”。

两轮都没有在问题之前说明：

- 上一轮执行了哪些发现方式，以及命令是否成功执行；
- 已重试多少次、发现了什么、排除了什么；
- 当前卡点是什么；
- 用户应如何在电视上开启 ADB，以及开启后如何继续。

这会让用户在相同选项之间反复尝试，却没有足够信息自行排除电视端设置问题。

补充观察：Agent 的普通对话上下文中可能已经包含上一轮情况，但弹出的选择组件会成为用户当前唯一的视觉焦点。上下文如果只出现在组件外的对话正文中，用户仍然很容易忽略它；因此这不是单纯的“上下文是否生成”问题，而是“关键上下文是否进入问题组件”问题。

### 期望行为

每一轮提问都必须先整理简短、可核对的上下文，并将其与唯一一个“问题 + 选项”共同放入当前交互组件或同一个连续的文字交互块中：

1. **上一轮结果**：做了什么检查、获得了什么结果；
2. **当前进度**：流程完成到哪一步、当前阻塞点是什么；
3. **处理指引**：用户现在可执行的具体解决步骤；
4. **本轮问题与选项**：优先使用平台原生选择组件，不支持时使用等价编号文字菜单。

首次提问没有“上一轮”时，也应明确写明“尚未执行设备检查”，并说明即将执行的检查范围。

对于弹窗、卡片、表单等原生选择组件，以上第 1 至第 3 项必须显示在组件内部，位于问题和选项之前。仅在组件外先发送一条普通对话消息，不视为满足要求。若平台的组件 API 只有“问题文本”和“选项”字段，应把压缩后的结果、进度和指引合并到问题文本中，而不是省略。

推荐的组件内信息顺序为：

```text
上一轮结果：第 3 次扫描完成，未发现 ADB 设备。
当前进度：电脑端检查已完成，正在等待电视开启网络调试并授权。
处理指引：设置 → 系统/关于本机 → 连点版本号约 7 次 → 开发者选项 → 开启 ADB/网络调试。

问题 S2-Q1：完成上述检查后，接下来怎么做？
[再次扫描设备] [提交电视 IP 地址] [查看完整指引] [安全退出]
```

### 未发现 ADB 设备时必须提供的文字指引

指引需使用用户可操作的语言，并提示不同品牌菜单名称可能不同：

1. 确认电视和运行 Agent 的电脑连接到同一个可信局域网；访客网络或开启了客户端隔离的 Wi-Fi 可能互相不可见。
2. 在电视中打开“设置”，进入“设备偏好设置 / 系统 / 关于本机”。
3. 连续点击“版本号 / Build”约 7 次，直到电视提示已开启开发者模式；部分电视会要求输入锁屏密码。
4. 返回“系统 / 开发者选项”，打开“USB 调试 / ADB 调试 / 网络调试 / 无线调试”中的对应开关。
5. 在“网络与互联网”或“关于本机”中查看电视 IP 地址。
6. Agent 发起连接后，在电视上核对并接受 RSA 调试授权提示；未授权、离线或仅端口可达都不能视为已连接。

如果平台支持图片展示，且能够获得与电视品牌、型号和系统版本匹配的可靠素材，可在文字步骤后附带标注截图或示意图。不得用不匹配的品牌界面冒充真实路径；缺少可靠截图时保留完整文字指引，并只在确有必要时用受约束选项询问品牌或系统类型。

### 跨平台内容对等要求

- 四个平台必须展示相同的结果摘要、进度、解决指引、问题 ID 和选项语义；仅允许因平台能力不同而改变展示形式。
- WorkBuddy、豆包工作若支持原生选择卡片，必须把摘要、进度和指引放入同一张卡片内部，并置于问题和选项之前；卡片外的普通对话正文不能替代卡片内上下文。
- Codex、Claude Desktop/Code 若无原生卡片，应输出等价的编号文字选项。
- 用户回答不明确、答非所问、使用旧问题的答案或输入格式错误时，不得推进状态或执行后续命令；应重新展示当前 `pending_question`，并保留更新后的结果摘要和处理指引。

### 待实现的数据字段建议

- `previous_result_summary`：上一轮执行与发现
- `progress_summary`：已完成步骤与当前阻塞
- `remediation_guidance`：与当前阻塞直接相关的解决步骤
- `evidence`：检查方式、次数和关键结果
- `visual_aid`：可选、来源可靠且与设备匹配的截图或示意图
- `component_context`：由上述字段压缩生成、必须随 `pending_question` 一同渲染的组件内上下文

### 验收标准

1. 每个交互回合的问题组件内部，在问题和选项之前包含“上一轮结果、当前进度、处理指引”；首次回合明确尚未检查。只在组件外显示不算通过。
2. `S2` 零设备结果显示本轮实际采用的发现方式、执行结果和累计尝试次数。
3. 首次未发现设备时即提供简要 ADB 开启检查；重复未发现时展示完整的电视端 ADB 开启与授权指引，再给出选项。
4. 所有截图或示意图都有可靠来源且与目标设备场景相符；无法确认时不伪造截图。
5. Claude Desktop/Code、Codex、WorkBuddy、豆包工作的信息内容对等，只有 UI 载体可以不同。
6. 无效回答只重显当前问题，不改变流程状态，也不触发下一步命令。
7. 未经用户明确选择和范围确认，不扩大到局域网扫描；选择扫描时先说明扫描范围和用途。

### 后续实现分组

- 扩展统一对话响应结构与渲染器；
- 为原生组件增加上下文内嵌适配，并为字段受限的平台提供问题文本合成降级；
- 补全 `S2` 无设备分支的分级排障文案；
- 增加可选视觉指引能力及素材可信度约束；
- 为四平台包补充内容对等和状态不前进测试；
- 分别在四个平台复测首次未发现、重复未发现、无效回答和恢复成功场景。

## UX-002：用户界面暴露过长且不可理解的内部方案 ID

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮用户截图中的 `PLAN-a239e10cdfa2` 同时出现在方案标题和确认问题中。截图未作为仓库资源持久化。

### 观察到的问题

`PLAN-a239e10cdfa2` 是适合机器校验和审计的内部标识，但长度较长、含义不直观。将其作为主要方案名称展示，会迫使非技术用户理解无意义的字母和数字，也会让不同模型自行缩写或改写名称。

### 固定命名规则

Skill 必须区分“内部不可变 ID”和“用户可见名称”，两者不得混用：

- 内部不可变 ID：继续使用 harness 生成的 `PLAN-<digest>`，用于计划完整性校验、日志、恢复和防止旧授权复用；不得由模型生成或修改。
- 用户可见名称：由渲染器按照固定模板生成，不允许模型自由命名。
- 固定模板：`方案 {两位会话序号}：{固定动作名称}`，例如 `方案 01：安装应用`。
- 允许在需要区分电视时扩展为：`方案 01：为客厅电视安装应用`；设备没有可信友好名称时使用“电视”，不把 IP、serial 或摘要哈希拼入主标题。
- 固定动作名称只能从枚举映射取得，例如 `安装应用`、`设置默认桌面`、`诊断应用`，不得由模型生成同义词。

内部 ID 可在“技术详情 / 诊断信息”中按需展开，但普通确认问题应写成“是否执行方案 01：安装应用？”，不能直接询问是否执行一串哈希 ID。

### 验收标准

1. 四个平台的普通用户界面和问题组件都使用相同的固定用户可见名称。
2. 同一会话中的方案序号从 `01` 递增，重复渲染同一方案时序号不变。
3. 模型不能创建、缩写、翻译或重写方案名称；名称只能由统一渲染器生成。
4. 内部 `PLAN-<digest>` 仍绑定设备、应用、动作和文件摘要，用户可见名称的简化不得削弱原有安全校验。
5. IP、ADB serial 和摘要哈希默认不进入方案标题；需要排障时只在技术详情中显示。

## UX-003：功能入口“电视清理”和“推荐配置”语义不清

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

### 观察到的问题

“电视清理”没有说明要清理什么，容易被理解为清理缓存、卸载应用、恢复出厂设置或修改桌面。“推荐配置”也没有说明它会展示应用、下载应用还是直接安装应用。

### 固定入口名称与说明

四个平台统一采用以下名称，不允许模型自行换同义词：

| 原名称 | 固定显示名称 | 组件内说明 |
| --- | --- | --- |
| 电视清理 | 设置电视默认桌面 | 查看当前桌面应用，并选择要设为默认桌面的应用；执行前另行确认。 |
| 推荐配置 | 查看并选择推荐应用 | 查看可用应用清单，选择需要下载的应用；选择后按应用名称二次确认。 |

“设置电视默认桌面”只能进入桌面相关流程，不能暗中扩大为卸载应用、删除数据、清理缓存或恢复出厂设置。“查看并选择推荐应用”不能在用户完成选择和二次确认前开始下载或安装。

### 验收标准

1. 四个平台使用完全一致的入口名称和组件内说明。
2. 每个名称准确描述紧接着发生的动作，不使用“清理”“配置”等无对象的概括词。
3. 选择入口本身不触发下载、安装、卸载、清除数据或更改默认桌面。
4. 旧名称仅可在版本迁移说明中出现，不能继续作为交互选项。

## UX-004：推荐应用缺少列表选择和按名称二次确认

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

### 观察到的问题

截图中的流程直接生成了包含 8 个应用、但“可执行安装项为 0 项”的计划，然后询问是否执行。应用表格在此处承担的是计划结果展示，而不是让用户选择要下载的应用；用户缺少一个明确的候选列表选择步骤，也没有看到按应用名称确认下载范围的独立问题。

### 期望流程

进入“查看并选择推荐应用”后，必须先展示当前可供用户选择的应用列表。每一项至少包含稳定编号、应用名称、版本和当前状态，例如“未安装 / 可更新 / 已是最新版本 / 暂不可下载”。没有合法下载源或处于 `pending_rights` 的应用应明确标注且不可选。

选择方式按平台能力固定降级：

1. 平台交互组件支持多选时，直接在同一个组件中提供应用多选列表。
2. 不支持多选时，展示带编号的完整列表，并要求用户用数字和顿号输入，例如 `1、2、3、4`。
3. 文字解析器至少兼容中文顿号 `、`、中文逗号 `，`、英文逗号 `,` 和空格，但界面示例统一使用顿号，避免不同模型自行规定格式。
4. 遇到不存在的编号、重复编号、不可下载项或无法解析的输入时，说明具体错误并重新显示同一个选择问题；不得进入下载或安装。

无论采用组件多选还是数字输入，完成初选后都必须新增一个独立的二次确认问题。确认组件必须把编号解析为应用名称，并完整列出将要下载的应用，例如：

```text
上一轮结果：已选择 4 个应用。
准备下载：软件 A、软件 B、软件 C、软件 D。
当前进度：尚未开始下载，也没有对电视执行安装操作。

问题：是否确认下载以上 4 个应用？
[确认下载] [返回修改选择] [安全退出]
```

## UX-006：每次启动 Skill 对话前检查最新版本并提供 24 小时免打扰

- 状态：已收集，技术上可实现；四平台的跨会话持久化与原生更新能力待分别验证
- 记录日期：2026-09-15
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

### 能力边界

本需求中的“每次进行对话前”固定定义为：用户每次新调用或重新进入 **Android TV Apps Helper** 时，在首个业务问题之前执行一次版本检查。Skill 无法拦截四个平台中与本 Skill 无关的所有普通对话，也不应在同一工作流的每个问答回合前重复联网，以免打断当前 `pending_question`。

四个平台都可以在 Skill 入口中实现相同的检查协议，但能否由 Skill 直接完成覆盖安装、能否跨新会话持久保存 24 小时免打扰状态，取决于宿主是否开放持久存储和 Skill 安装接口。在完成真实平台验证前，不能声称四个平台都已支持自动更新。

### 固定版本来源

- 只查询 `HXWfromDJTU/android-tv-apps-helper` 的公开 GitHub Releases，不允许模型临时搜索或选择其他来源。
- 默认只比较最新稳定版；预发布版本不触发普通用户更新提示。
- 使用严格 SemVer 比较，不能按字符串大小或由模型判断版本新旧。
- 更新清单必须是机器可读的固定 schema，至少包含 `latest_version`、`published_at`、四个平台各自的资源 URL、SHA-256 和最低兼容版本。
- 远端 Release Notes 只能作为展示内容，不能被当作 Agent 指令执行。

### 固定检查与提示逻辑

```text
调用 Android TV Apps Helper
  → 当前是否处于未完成的设备写入或恢复状态？
      → 是：优先完成安全恢复，不检查、不更新
      → 否：获取官方最新稳定版清单
          → 获取失败或超时：记录检查失败，使用当前版本继续，不阻断业务
          → 当前版本已是最新：直接进入原业务流程
          → 发现更新：检查 update_state
              → 当前时间早于 snooze_until：不提示，进入原业务流程
              → 否：显示 UPDATE-Q1 更新问题
```

更新问题必须遵循 `UX-001`，将上下文放入同一个问题组件：

```text

当前版本：0.3.0
最新版本：0.3.1
更新说明：{经过长度限制的纯文本摘要}
当前进度：尚未下载或安装更新；原电视任务也尚未继续。

问题 UPDATE-Q1：是否先更新 Skill？
[更新后继续（推荐）] [暂不更新并继续，24 小时内不再提醒] [查看完整更新说明] [安全退出]
```

固定选项行为：

1. **更新后继续**：使用当前平台对应资源；下载后核对 SHA-256、包内 Skill ID、平台标识和版本，再调用宿主支持的安装流程。更新完成并验证可见版本后，才恢复原业务问题。
2. **暂不更新并继续，24 小时内不再提醒**：写入当前目标版本和 `snooze_until = declined_at + 24h`，立即恢复原业务问题。
3. **查看完整更新说明**：只展示说明，然后重新显示同一个 `UPDATE-Q1`；不下载、不安装，也不开始电视任务。
4. **安全退出**：停止本次 Skill 工作，不下载更新，也不执行电视命令。

用户未明确回答、回答不属于当前选项或使用旧问题答案时，保持 `UPDATE-Q1`，不得开始更新或推进电视工作流。

### 24 小时免打扰状态

宿主适配器应以原子方式持久化以下字段：

- `installed_version`
- `latest_seen_version`
- `declined_version`
- `declined_at`
- `snooze_until`
- `last_check_at`
- `last_check_result`

免打扰按“用户 + 平台 + Skill + 被拒绝的目标版本”记录。用户拒绝后 24 小时内仍可执行只读版本检查，但不得再次弹出更新问题。满 24 小时后，如果当前版本仍落后，则在下一次调用 Skill 时再次提示。

如果宿主没有跨会话持久存储能力，只能做到当前会话免打扰，不能假装已经满足 24 小时规则；该平台应标记为兼容性阻塞，直到提供可靠存储适配。

### 更新安全约束

- 永不静默自动更新；必须由用户选择“更新后继续”。
- 版本检查是只读网络请求；更新下载和安装是独立的、用户明确批准的动作。
- 下载失败、摘要不符、平台包不匹配、安装失败或新版本不可见时，保留当前可用版本并显示失败原因。
- 更新过程中不得执行 ADB 写操作；如有未完成的安装计划，更新后必须重新校验会话 schema、目标设备、APK 摘要和计划有效性。
- Skill 包不能仅凭自己输出“更新完成”；必须读取宿主实际可见的已安装版本作为证据。
- GitHub 不可达时使用当前已安装版本继续，不把网络失败误报为“已经是最新版”。

### 跨平台降级

1. 宿主支持由 Agent 安装 Skill：用户确认后走宿主原生安装，并验证版本。
2. 宿主只支持上传 ZIP 或人工安装：用户确认后提供唯一对应平台的资源、SHA-256 和固定安装步骤；安装前暂停电视任务，安装完成后重新调用并验证。
3. 宿主不允许 Skill 联网：显示“本平台无法自动检查版本”，可提供固定的手动检查入口，但不伪造检查结果。
4. 宿主不提供跨会话持久化：明确标为不满足 24 小时免打扰，不能降级成每次都重复提示。

### 验收标准

1. 每次新调用或重新进入本 Skill 时，在首个业务问题之前恰好执行一次版本检查；同一连续工作流中不逐轮重复检查。
2. 发现新稳定版时，更新问题和版本上下文位于同一个交互组件内。
3. 用户拒绝的目标版本在接下来 24 小时内不再次弹窗；24 小时后仍落后才重新提示。
4. “查看说明”、无效回答和网络失败都不会触发下载、安装或 ADB 命令。
5. 未经明确确认不更新；确认更新也只使用当前平台匹配且校验通过的官方资源。
6. 更新完成、失败、当前已是最新和无法检查四种结果必须分别展示，不能混用。
7. 若入口时存在未完成的设备写入或恢复状态，安全恢复优先于版本检查。
8. Codex、Claude Desktop/Code、WorkBuddy、豆包工作分别验证：联网检查、版本比较、拒绝后跨会话 24 小时免打扰、确认更新、失败回滚和原问题恢复。

## UX-007：首次问题前应自动完成只读预检查并在组件内展示结果

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）

### 观察到的问题

安全的只读预检查本身不需要用户先批准。把“是否开始预检”作为首次问题，会增加一个无法帮助用户作出业务选择的回合，也违背“问题组件应承载当前事实和阻塞点”的要求。

首次有意义的问题应建立在已经执行完成的预检查结果上，而不是询问是否开始检查。组件要让非技术用户直接看懂：电脑端是否具备条件、当前网络发现了什么设备、其中哪些可能是电视、是否已经存在已授权的 ADB 连接，以及接下来需要用户确认什么。

### 固定启动顺序

```text
调用 Android TV Apps Helper
  → 处理未完成的设备写入或安全恢复（如有）
  → 执行 UX-006 版本检查（到达安全检查点时）
  → 自动执行安全、只读、有限范围的 PRECHECK
  → 生成结构化检查结果
  → 在首次问题组件内展示结果、确认事项和操作指引
  → 等待用户明确回答当前问题
```

旧的 `S0-Q1：是否开始只读预检？` 应取消。预检查成功、部分成功或失败都必须先产生明确结果，再进入对应的首次问题；不能因为某一项不可用而只抛出空白选择。

### 自动预检查的固定范围

无需再次征求同意即可执行的只读项目：

1. 检查当前 Agent 是否运行在能够访问本机网络和 ADB 的执行环境。
2. 检查 ADB 是否已安装、可执行，并记录版本或具体错误。
3. 执行 `adb devices -l`，列出已经被 ADB 发现的设备及 `device / unauthorized / offline` 状态。
4. 读取电脑当前活动网络接口和本机地址；在宿主允许且不会暴露敏感凭据时，显示当前 Wi-Fi 名称。
5. 读取本机已有的邻居缓存、ADB 已知目标和被动 mDNS/服务发现结果，整理“可能的电视设备”。

自动预检查不得主动扫描整个子网、探测所有 IP 或尝试连接未经用户选择的地址。需要主动局域网扫描时，必须另设问题，说明扫描的网段、端口、用途和范围，得到明确选择后才能执行。

### 检查结果的固定展示结构

首次问题组件必须至少显示：

| 项目 | 固定结果类型 | 用户可见示例 |
| --- | --- | --- |
| 执行环境 | 可访问本机 / 仅云端 / 无法判断 | 当前在本机运行，可以检查电视连接。 |
| ADB 工具 | 可用 / 不可用 / 检查失败 | ADB 已安装，版本 1.0.41。 |
| 当前网络 | 已连接 / 未连接 / 无法读取 | 电脑已连接 Wi-Fi“家庭网络”。 |
| 已发现设备 | 数量与状态 | 发现 2 个网络设备，其中 1 个可能是电视。 |
| ADB 电视 | 已授权 / 未授权 / 离线 / 未发现 | 未发现已授权的 ADB 电视。 |
| 检查范围 | 被动、有限范围 | 未主动扫描整个局域网，也未向电视发送修改命令。 |

不得把邻居缓存中的普通设备直接断言为电视。识别依据不足时使用“可能是电视 / 未能确认设备类型”，并显示名称、IP 或发现方式等可核对信息。未发现设备也不能断言电视没有开启 ADB，只能说明当前检查没有发现可用连接。

问题 PRECHECK-Q1：电脑和电视目前是否连接到同一个 Wi-Fi？

```text
上一轮结果：你已确认电脑和电视连接到同一个 Wi-Fi。
当前进度：网络条件已确认；尚未发现已授权的 ADB 连接。

开启 ADB：电视设置 → 系统/设备偏好设置 → 关于本机 → 连续点击版本号约 7 次 → 返回开发者选项 → 开启 ADB/网络调试。随后接受电视上的 RSA 授权提示。

问题 PRECHECK-Q2：电视目前是否已开启 ADB 或网络调试？
[已开启，重新检查] [尚未开启] [不确定，查看完整指引] [安全退出]
```

### 指引载体

- 问题组件中始终保留足以完成操作的简要文字步骤，不能只给外部链接。
- 可同时提供项目内固定文档链接，文档需公开可访问、与当前 Skill 版本对应，并包含不同电视系统的菜单差异说明。
- 宿主支持图片时，可在同一组件或紧邻组件的位置展示可靠的步骤示意图；图片必须标明适用品牌或“通用示意”，不能伪装成用户电视的真实界面。
- 如果品牌差异导致通用步骤无法继续，应使用受约束选项询问品牌或系统类型，再展示匹配指引，不要求用户自由描述一大段设备信息。

### 失败与降级

- ADB 不可用：显示具体缺失项和安装/修复指引，然后询问“完成后重试 / 查看完整安装指引 / 安全退出”。
- 宿主仅能在云端运行：明确说明无法检查用户局域网，优先引导切换到本机执行环境，不生成虚假的设备列表。
- 无法读取 Wi-Fi 名称：显示“无法读取”，通过问题请用户人工确认，不把未知写成已连接。
- 未发现设备：显示已执行的检查、当前限制和 ADB 开启步骤，再提供重新检查、提交电视 IP、申请有限范围扫描或安全退出。

### 验收标准

1. 启动 Skill 后不再出现“是否开始只读预检”的空前置问题。
2. 首次有意义的问题之前已自动执行预检查，并在同一个组件内展示真实结果。
3. 结果明确区分已确认电视、可能是电视、普通设备和无法识别，不夸大探测能力。
4. 预检查只使用固定的被动或有限范围方法；主动局域网扫描仍需明确范围授权。
5. 同一 Wi-Fi 与 ADB 开启状态分两轮确认，每轮只有一个问题和固定选项。
6. ADB 指引至少包含可直接执行的文字步骤；链接或图片是增强项，不替代文字。
7. 检查失败、云端环境和权限不足都有清楚的结果与恢复选项，不展示虚假成功。
8. Claude Desktop/Code、Codex、WorkBuddy、豆包工作的预检查字段、问题顺序和降级语义保持一致。

## UX-008：收尾选项含义重叠，应按用户目标分层精简

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮截图中的 `S11-Q1` 同时提供“结束并关闭调试”和“保持现状退出”，两者都以结束会话为主要结果，但没有在组件内清楚解释关闭 ADB 的后果。截图未作为仓库资源持久化。

### 观察到的问题

“结束并关闭调试”和“保持现状退出”在内部动作上并不相同：前者还会关闭电视的 ADB 调试，后者只结束 Skill 会话。但对普通用户来说，两项都首先表达“退出”，差异被藏在“关闭调试 / 保持现状”这类抽象词中，容易被误认为重复，也难以判断应该选择哪一个。

同一层级还混入“回退到小米桌面”这一具体设备变更，使首个收尾问题同时承担“是否结束”和“结束前修改哪些电视设置”两个决策。

### 精简原则

- 一个问题只解决一个用户决策，不在同一层混合“是否继续”和多个退出前变更。
- 选项名称使用“动作 + 对象 + 结果”，不单独使用“清理、保持现状、关闭调试”等需要猜测的术语。
- 顶层收尾问题最多保留 3 个语义互斥的固定选项。
- 会改变电视状态的收尾动作使用结果明确的名称，并继续遵守明确授权和结果验证要求。
- 每个选项的组件内说明都要指出会保留什么、会改变什么以及是否还能再次连接。
- 关闭 ADB 和开发者模式不再作为普通退出选项，而是所有结束路径共同进入的独立安全收尾步骤，具体规则见 `UX-010`。

### 固定收尾流程

`S11-Q1` 精简为：

```text
上一轮结果：{本次已完成、失败和未执行事项的摘要}
当前电视状态：{默认桌面、ADB 调试和壁纸的已确认状态}

问题 S11-Q1：接下来要做什么？
[结束本次任务，保留当前桌面和壁纸]
[继续其他电视操作]
[恢复本次会话开始时的桌面后结束]
```

三个选项的固定含义：

1. **结束本次任务，保留当前桌面和壁纸**：不更改默认桌面、壁纸或应用，然后进入 `UX-010` 的 ADB 与开发者模式安全收尾。
2. **继续其他电视操作**：返回任务选择；不得把已经完成的动作自动加入新任务。
3. **恢复本次会话开始时的桌面后结束**：先展示恢复计划并取得明确批准；恢复完成或用户取消后，再进入 `UX-010` 的安全收尾。恢复不会卸载 Emotn UI。

恢复目标必须是首次只读盘点记录的确切 HOME。它可能是厂商桌面，也可能是用户此前安装的第三方桌面；没有额外身份依据时，不得称为“原厂”或“OEM”，也不得仅凭截图、IP 或猜测硬编码品牌名称。

选择恢复会话开始时的桌面后，仍需展示具体变更摘要并取得执行确认。所有需要 ADB 的验证和恢复动作完成后，才进入关闭 ADB 与开发者模式的用户操作指引。

### 应删除或替换的旧文案

| 旧选项 | 处理方式 | 新位置或名称 |
| --- | --- | --- |
| 结束并关闭调试 | 从顶层移除 | 所有结束路径统一进入 `UX-010` 的安全收尾 |
| 保持现状退出 | 改为具体结果 | `S11-Q1`：结束本次任务，保留当前桌面和壁纸 |
| 回退到小米桌面 | 避免品牌硬编码 | `S11-Q1`：恢复本次会话开始时的桌面后结束 |
| 继续其他任务 | 明确对象 | `S11-Q1`：继续其他电视操作 |

### 验收标准

1. `S11-Q1` 不再同时出现两个以“退出”为主要含义的选项。
2. 顶层仅包含“结束并保留桌面和壁纸、继续操作、恢复会话开始桌面后结束”三个明确目标。
3. 关闭 ADB 不再与普通退出选项并列；所有结束路径都进入 `UX-010` 的独立安全收尾。
4. 选择“结束并保留当前桌面和壁纸”不会发送新的桌面、壁纸或应用写命令。
5. 关闭 ADB 和开发者模式在所有远程验证完成后提示，并说明关闭后无法继续远程连接。
6. 默认桌面名称来自已验证设备信息，不由模型猜测品牌。
7. 每个选项在四个平台上使用相同的名称、说明和状态转移。

## UX-009：每轮重要信息和最终结果必须优先用表格呈现

- 状态：已收集，纳入统一交互呈现层，待设计确认后实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮截图中的最终结果以多段连续文字叙述设备信息、桌面变更、验证结果、过程问题和保留项，虽然内容完整，但用户难以快速区分成功、失败和保留状态。截图未作为仓库资源持久化。

### 观察到的问题

长段文字要求用户逐句阅读后自行提炼结论。即使句中包含若干绿色对勾，事项、最终状态、证据和后续动作仍混杂在一起，尤其容易产生以下误解：

- 中途失败但后来恢复的步骤，会被误认为最终仍然失败；
- “安装存在”“已启动”“现场画面正常”等不同证据等级被压缩到一句话中；
- 未执行、主动保留和尝试失败没有稳定的视觉区别；
- 真正需要用户处理的阻塞点没有优先显示。

### 固定呈现规则

每一轮 Agent 回复都必须先把本轮最重要的信息整理为表格，再显示必要的补充说明、当前问题和选项。禁止先输出大段过程叙述，再在末尾给结论。

优先级固定为：

1. **关键状态表**：本轮完成、失败、等待确认和保留的核心事项；
2. **阻塞或处理指引**：只写与当前问题直接相关的操作；
3. **当前问题和选项**：遵守 `pending_question`；
4. **技术详情**：命令、包名、serial、原始错误和日志摘要，默认放在结果之后或“查看技术详情”分支中。

表格默认控制在 3 至 6 行。内容过多时拆成“关键结果”和“技术详情”两张表，不能把几十项内容塞进一个横向滚动的大表。

### 固定状态符号

| 符号 | 固定含义 | 使用约束 |
| --- | --- | --- |
| ✅ | 已完成 | 已达到该行所声明的证据标准；不能用来表示仅已开始或推测成功。 |
| ❌ | 尝试后仍未完成 | 已实际尝试且截至本轮结束仍失败；必须附简短原因或下一步。 |
| ⚠️ | 部分完成或等待用户确认 | 例如安装成功但尚未完成画面、声音或遥控器现场验收。 |
| ⏳ | 尚未开始或正在等待 | 仍在计划内，但尚未执行或正在等待输入。 |
| ⏭️ | 明确跳过或不适用 | 用户选择跳过、当前设备不适用，或因权利状态不可执行。 |

至少必须使用用户要求的两种核心符号：已完成为 ✅，尝试后最终未完成为 ❌。其他符号用于避免把“未执行、等待验收、主动跳过”错误标成失败。

如果某一步第一次失败、随后重试成功，其最终事项标为 ✅，并在结果中写“重试后完成”；只有恢复后仍失败才标为 ❌。状态必须由 harness 中的执行记录和证据等级计算，不能由模型根据语气自行选择 emoji。

### 每轮问题组件模板

平台支持原生表格时使用原生表格；否则至少使用 Markdown 表格。表格必须位于原生问题卡片内部；如果宿主不支持在问题组件内渲染表格，应把表格放在与问题紧邻的同一回复中，并在组件内重复一行最关键阻塞点。该限制必须在平台验证报告中如实标记，不能声称完全对等。

```markdown
| 状态 | 检查事项 | 本轮结果 |
| --- | --- | --- |
| ✅ | ADB 工具 | 已安装，版本 1.0.41 |
| ✅ | 当前网络 | 已连接“家庭网络” |
| ⚠️ | ADB 电视 | 尚未发现可确认的连接 |

**当前阻塞：** 请确认电视和电脑连接到同一个 Wi-Fi，并在电视上开启 ADB 调试。

问题 PRECHECK-Q1：电视和电脑是否连接到同一个 Wi-Fi？
[是] [不是] [不确定，查看方法] [安全退出]
```

当某项只是“没有检查到”而非“实际尝试失败”时，不直接使用 ❌。例如被动发现没有找到电视应写成 `⚠️ 未发现可确认的电视`；只有用户选择连接某个目标且连接最终失败时，才写 `❌ 连接电视失败`。

### 最终报告模板

最终回复先展示任务结果表：

```markdown
| 状态 | 事项 | 最终结果 | 证据 |
| --- | --- | --- | --- |
| ✅ | 安装 Emotn UI | 已安装 1.1.0.1 | 包名和版本已核对 |
| ✅ | 设置默认桌面 | 已切换为 Emotn UI | Home 键和前台 Activity 已验证 |
| ⚠️ | 现场使用 | 等待用户确认画面和遥控器 | 尚无现场验收 |
| ❌ | 设置自定义壁纸 | 传输后设置失败 | 系统返回权限错误 |
| ⏭️ | 卸载原厂桌面 | 按安全策略保留 | 未执行卸载或禁用 |
```

如有过程异常，再使用第二张简表说明是否已解决：

```markdown
| 过程异常 | 最终处理 |
| --- | --- |
| 首次 ADB 连接返回 `No route to host` | ✅ 重启本机残留 ADB server 后连接成功 |
| MIUI 覆盖默认桌面设置 | ✅ 使用已批准的兼容方式后生效 |
```

技术信息，例如 IP、serial、包名、完整命令、stdout/stderr 和日志路径，不与主结论混写；仅保留必要摘要并提供“查看技术详情”入口。

### 与证据等级的关系

- `file_validated`：只能把“文件校验”标为 ✅，不能据此把“安装”标为 ✅。
- `installed`：只能确认包和版本存在。
- `launched`：只能确认应用被启动或处于前台。
- `runtime_signal`：只能确认已有相应运行信号。
- `on_site_accepted`：只有用户确认画面、声音和遥控器后，才能把“现场使用正常”标为 ✅。

表格中的每一个 ✅ 都必须绑定其中一个明确的证据等级或确定的只读检查结果。

### 跨平台实现

- 统一核心生成结构化 `summary_rows`，每行包含 `status`、`item`、`result`、`evidence` 和可选 `next_action`。
- 四个平台适配器只能改变表格载体，不能修改状态符号、事项含义或删掉失败项。
- WorkBuddy、豆包工作优先使用组件内原生表格或可渲染的 Markdown 表格。
- Codex、Claude Desktop/Code 使用同样的 Markdown 表格；平台原生组件可在表格之后承载问题选项。
- 表格无法渲染的平台必须在实测中标记降级效果，并至少保持清晰的行列结构，不能退回连续长段落。

### 验收标准

1. 每轮回复的重要结果先以表格展示，最终报告不能只由连续段落构成。
2. 已完成事项显示 ✅；实际尝试且最终仍失败的事项显示 ❌。
3. 中途失败但已恢复的事项最终显示 ✅，并注明“重试后完成”。
4. 未执行、等待现场确认和主动跳过不会被误标成 ❌ 或 ✅。
5. 每个 ✅ 都有与该结论匹配的检查结果或证据等级。
6. 问题组件仍包含上一轮结果、当前阻塞和处理指引；表格不能替代 `UX-001` 的上下文要求。
7. 最终结果、过程异常和技术详情分层呈现，关键结论不被日志淹没。
8. 四个平台针对成功、最终失败、重试后成功、未执行和等待验收五类固定样例进行渲染快照验证。

## UX-010：任务结束前必须指导用户关闭 ADB 和开发者模式

- 状态：已收集，纳入安全收尾流程，待设计确认后实现
- 记录日期：2026-09-15
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 关联反馈：修订 `UX-008`，关闭调试不再是普通退出选项，而是所有结束路径都必须经过的安全步骤

### 目标

任务结果展示完成后，Skill 不能直接结束。只要电视的 ADB 或开发者模式仍处于开启或无法确认的状态，就必须主动提醒用户在电视端关闭，并根据已经验证的电视品牌、型号、Android 版本和系统界面提供对应操作方式。

关闭提示必须发生在所有依赖 ADB 的安装、验证、恢复、日志收集和报告保存完成之后，避免提前断开连接导致收尾操作无法完成。

### 固定安全收尾顺序

```text
生成并保存最终报告
  → 完成所有仍需 ADB 的验证和恢复动作
  → 只读检查 ADB 与开发者模式当前状态
  → 根据已验证设备信息匹配关闭指引
  → 在同一个问题组件内显示状态表和型号对应步骤
  → 等待用户在电视端操作并明确反馈
  → 记录用户确认或未完成状态
  → 结束 Skill 会话
```

Agent 不应默认通过远程命令替用户关闭开发者模式。关闭 ADB 会中断远程连接，且不同厂商对开发者选项的实现不同；默认采用“用户在电视端主动关闭，Agent 提供型号对应指引”的方式。

### 设备指引匹配规则

在连接仍然可用时，读取并保存以下已验证字段：

- `manufacturer`
- `model`
- `android_version`
- `sdk`
- 可可靠识别时的系统界面或固件系列
- 当前默认 Launcher

统一维护版本化的设备关闭指引注册表，至少包含：

- 匹配条件：厂商、型号或型号族、Android/系统版本范围；
- 进入设置的遥控器路径；
- 关闭 `ADB 调试 / 网络调试 / 无线调试` 的步骤；
- 关闭开发者模式总开关的步骤；
- 某型号不存在总开关时的明确说明；
- 可靠来源链接、核验日期和可选示意图；
- 操作完成后的用户可见结果。

匹配优先级固定为“精确型号与系统版本 → 型号族 → 厂商系统 → 通用 Android TV 指引”。未匹配到精确型号时，必须明确写“暂未找到该型号的精确指引”，再提供标为通用的步骤或受约束的系统类型选择；禁止模型凭经验编造型号专属菜单路径。

### 结束问题组件

必须遵守 `UX-001` 和 `UX-009`，在同一个组件内先显示表格，再显示型号指引和问题：

```markdown
| 状态 | 安全事项 | 当前结果 |
| --- | --- | --- |
| ⚠️ | ADB / 网络调试 | 当前连接仍然有效，需要在电视端关闭 |
| ⚠️ | 开发者模式 | 尚未确认关闭 |

**电视：** 小米电视 MiTV-ASTP0（Android 9）

**关闭方式：**
1. 使用遥控器打开电视“设置”。
2. 按本型号已核验路径进入“开发者选项”。

问题 FINISH-SAFETY-Q1：你是否已经在电视上关闭 ADB 和开发者模式？
[两项都已关闭]

```

示例中的菜单路径只是模板占位，实际显示时必须来自与目标设备匹配并经过核验的指引注册表。

### 回答处理

1. **两项都已关闭**：记录用户现场确认。ADB 随后不可达可以作为辅助信号，但连接断开本身不能证明一定是用户关闭了 ADB；最终结论应写“用户确认已关闭”。
2. **找不到设置，查看本型号详细指引**：保持同一个 `pending_question`，显示更详细文字、可靠文档链接和可用的标注示意图；不得直接结束。
3. **暂时保持开启并结束**：再次明确局域网内调试访问风险，记录为 ⚠️“用户选择暂时保留”，然后允许结束；不能显示 ✅“安全设置已完成”。
4. 用户回答不明确时：重显相同状态表、型号步骤、问题与选项，不得推断已经关闭。

如果用户确认关闭后仍可稳定执行新的 ADB 命令，应提示“ADB 似乎仍处于开启状态”，重新显示当前问题；不得直接把用户回答覆盖为成功，也不能在没有进一步证据时指责用户操作错误。

### 文档与图片要求

- 每个已支持型号至少提供完整文字步骤；外部链接或图片不能替代文字。
- 文档链接优先使用电视厂商官方支持页面；无官方页面时，项目内文档必须标明验证设备、系统版本、来源和核验日期。
- 示意图必须标注适用型号或“通用示意”，不得把其他品牌截图当作目标电视真实界面。
- 主问题组件只显示简短步骤；完整指引通过“查看本型号详细指引”展开，避免最终页面再次变成长段文字。

### 最终报告状态

| 用户结果 | 最终表格状态 |
| --- | --- |
| 用户确认两项都已关闭，且无相反证据 | ✅ ADB 与开发者模式已由用户确认关闭 |
| 用户尝试关闭但仍能稳定连接，或明确表示操作失败 | ❌ 尝试关闭但尚未完成，并显示下一步 |
| 用户选择暂时保留，或系统状态无法确认 | ⚠️ 尚未关闭或无法确认，不显示安全完成 |

### 验收标准

1. 所有结束任务路径都经过 `FINISH-SAFETY-Q1`，不能从最终报告直接结束。
2. 安全组件内同时显示 ADB 和开发者模式的当前状态、目标电视友好名称和对应关闭步骤。
3. 关闭指引由确定性设备注册表匹配，模型不能自由生成型号专属路径。
4. 没有精确型号指引时明确降级为型号族、厂商或通用指引，并标示匹配层级。
5. 用户找不到设置时保持当前问题，提供详细文档或可靠示意图。
6. 用户暂时保留时可以结束，但最终报告必须显示 ⚠️，不能显示安全完成。
7. 用户确认、ADB 断连信号和实际可达性分别记录，不把单一断连当作关闭证明。
8. 四个平台针对精确型号匹配、通用降级、用户确认关闭、仍可连接、暂时保留和无效回答进行相同状态测试。

## UX-011：修改壁纸和 Home 键前必须展示型号级兼容性风险

- 状态：已收集，系统名称待用户确认后写入兼容性规则
- 记录日期：2026-09-15
- 观察来源：用户基于当前 Codex 实机执行结果反馈
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

### 用户观察

用户反馈当前实机经验为：

1. 用户称为“小米 Harmony OS 2.0”的系统上，壁纸替换成功率相对较高；该系统名称需进一步确认，不能直接作为程序匹配键。
2. 其他电视系统可能受到原生桌面、广告入口和厂商策略限制，壁纸替换成功率较低。
3. Home 键默认指向的限制通常比单纯设置壁纸更严格，存在较高失败概率。

以上内容目前属于用户提供的实机观察，不直接转换为适用于所有品牌和型号的统计结论。Skill 只能依据版本化兼容性注册表展示“已验证、风险较高或兼容性未知”，不能由模型把单次结果扩写成通用成功率。

### 两类动作必须分开评估

壁纸替换与 Home 键指向是两个独立动作，不能使用一个笼统的“桌面兼容性”结论：

| 动作 | 主要限制 | 独立结果 |
| --- | --- | --- |
| 设置自定义壁纸 | 壁纸权限、Launcher 实现、系统或桌面更新后恢复 | `wallpaper_compatibility` |
| 修改 Home 键默认指向 | 厂商默认桌面策略、系统级 HOME 角色、广告入口或设备管理限制 | `home_key_compatibility` |

用户同时选择两项时，问题组件也必须分别展示两行风险和两项预期结果。确认尝试其中一项，不能被解释为同时批准另一项。

### 兼容性注册表

统一维护版本化、可测试的设备兼容性注册表，匹配字段至少包括：

- 厂商与硬件型号；
- Android 基础版本、SDK 和构建 ID；
- 可确认时的系统品牌、固件版本和当前 Launcher；
- 动作类型：壁纸或 Home 键指向；
- 结果等级：`verified_supported`、`high_risk`、`unknown`；
- 实测次数、最近验证日期、成功或失败证据摘要；
- 已知失败表现、恢复方法和证据来源。

风险等级必须由注册表和设备指纹确定，不能由模型临场判断：

- `verified_supported`：相同或明确兼容的设备/系统组合有足够实测成功证据，但仍不承诺永久有效。
- `high_risk`：相同设备/系统组合有明确限制或重复失败证据，可提示“大概率无法成功”。
- `unknown`：没有足够匹配证据，只能提示“兼容性未知、可能失败”，不能虚构概率。

### 执行前兼容性风险门

用户选择修改壁纸或 Home 键指向后，在生成和批准执行计划之前，必须先读取已验证设备信息、匹配兼容性注册表，并显示独立的 `COMPATIBILITY-RISK-Q1`。风险信息必须位于同一个问题组件内部，并遵守 `UX-009` 的表格规范。

```markdown
| 状态 | 设备与操作 | 兼容性判断 |
| --- | --- | --- |
| ✅ | 电视型号 | 小米电视 MiTV-ASTP0，Android 9，构建版本 {已验证值} |
| ⚠️ | 替换壁纸 | 风险较高：该系统可能阻止设置，或在几天后恢复默认壁纸 |
| ⚠️ | 修改 Home 键 | 风险很高：厂商桌面策略可能覆盖或拒绝默认 HOME 变更 |

**重要提示：** 当前型号对应的实测记录显示，这些修改大概率无法稳定生效。失败时会保留原厂桌面，不卸载、不禁用、不清除数据。

问题 COMPATIBILITY-RISK-Q1：是否仍要尝试上述修改？
[了解风险，仍然尝试]
[只尝试替换壁纸]
[只尝试修改 Home 键]
[取消并返回任务选择]
```

示例中的“大概率无法稳定生效”只能在匹配结果为 `high_risk` 时显示。匹配结果为 `unknown` 时必须改为“当前没有该型号的可靠兼容性记录，结果未知且可能失败”；匹配结果为 `verified_supported` 时仍需显示可能被系统重置的提醒。

### 高亮与确认规则

- 电视厂商、型号、Android/系统版本和构建 ID必须位于表格中，不能只藏在技术详情。
- 风险预测使用 ⚠️；❌ 只用于已经尝试且最终仍未完成，不能把尚未执行的高风险动作标为失败。
- `high_risk` 时必须出现“大概率无法成功”或等价的固定高风险文案，并明确说明具体受限动作。
- 用户必须选择当前风险问题中的明确选项；“继续、好的、你决定”等不能通过。
- 用户确认风险后才生成安装或设置计划；计划仍需单独批准，风险确认不能代替执行批准。
- 执行失败时最多进行一次已定义的安全重试，然后停止并展示真实结果和恢复状态。

### 安全边界

- 不因兼容性较低而尝试 root、刷机、清除数据、卸载或禁用原厂 Launcher。
- Home 键设置失败时，保留可用的原厂桌面和现有 HOME 入口。
- 壁纸设置失败或被系统恢复时，不反复后台重写壁纸，也不声称永久生效。
- 对同一型号产生新的、经过验证的结果后，可以更新兼容性注册表；不能让模型直接修改风险等级。

### 验收标准

1. 壁纸与 Home 键修改在执行计划之前分别经过型号级兼容性判断。
2. 风险组件高亮展示厂商、型号、系统版本、两项动作的独立风险和证据来源。
3. 只有注册表匹配为 `high_risk` 时才显示“大概率无法成功”；未知设备不伪造成功率。
4. 用户可选择同时尝试、只尝试壁纸、只尝试 Home 键或取消，且每种选择生成不同计划。
5. 风险确认与实际执行批准分开，任何模糊回答都不能推进。
6. 失败时保留原厂桌面，不使用 root、刷机、清除数据或后台反复重写。
7. 四个平台使用同一设备指纹、风险注册表、固定文案和状态转移。

## UX-012：当贝市场应由 Skill 解析官方稳定下载源

- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

2026-09-15 查询当贝官网所得：

| 项目 | 已核实结果 |
| --- | --- |
| 官方产品入口 | `https://www.dangbei.com/` |
| 官网显示版本 | `6.0.7` |
| 官网显示更新日期 | `2026-07-06` |

官网本身把上述 CDN 地址作为“立即下载”目标，因此可以把它作为官方页面解析出的上游下载源。当前没有找到当贝市场的官方 GitHub Release，也没有找到允许本项目直接重新托管 APK 的明确公开许可。

### 固定分发策略

为 catalog 新增 `official_direct` 模式，表示“由发布者官网明确提供或链接的下载资源，但本项目没有再分发授权”。当贝市场从 `pending_rights` 改为此模式的前提是取得 APK 并完成包体身份验证。

`official_direct` 必须记录：

- 发布者官方产品页；
- 官方页显示的版本和更新时间；
- 官方页解析出的下载 URL；
- 允许的下载主机名单；
- APK 字节大小和 SHA-256；
- 包名、versionName、versionCode、最低 SDK、ABI 和签名证书摘要；
- 来源核验时间和下一次复核时间。

当贝市场不上传到本项目 GitHub Release，除非后续获得明确的再分发许可。Skill 直接从当贝官网当前确认的上游地址下载，并在安装前执行完整 APK 校验。官方页面允许下载不等于允许第三方重新托管。

### 运行时解析与下载

1. 从 catalog 中读取固定官方产品页和允许主机。
2. 获取官方产品页，解析当前稳定版本和下载目标。
3. 下载目标必须位于允许主机名单；跳转到未登记主机时停止。
4. 下载 APK 后验证 ZIP 结构、AndroidManifest、包名、版本、签名证书摘要、字节大小和 SHA-256。
5. 版本或签名与 catalog 不符时停止安装并标记“官方资源已变化，需要项目维护者复核”。
6. 验证通过后才进入用户的按名称下载确认和独立安装批准流程。

运行时不能通过开放式网页搜索寻找 APK，也不能采用第三方网盘、论坛附件或未知 GitHub 镜像。

### 用户交互变化

当贝市场不再显示“请提供本地 APK”。正常状态下显示：

```markdown
| 状态 | 应用 | 下载来源 |
| --- | --- | --- |
| ✅ | 当贝市场 6.0.7 | 当贝官网稳定版 |

问题：是否把“当贝市场 6.0.7”加入下载清单？
[加入下载清单] [查看官方来源] [返回应用列表] [安全退出]
```

官方 CDN 当前不可达或返回异常时显示真实结果，并提供：

- 重试官方来源；
- 打开当贝官方产品页；
- 暂时跳过并继续其他应用；
- 安全退出。

“提供本地 APK”可以保留为高级、非默认恢复路径，但不能再作为普通用户解决官方来源问题的主要选项。

### 安全与维护边界

- 只使用当贝官网当前明确链接的稳定版，不使用搜索结果中的任意 APK。
- 官网版本变化时先进入 catalog 维护和验证，不让模型自动信任新包。
- 下载确认与安装确认保持独立。
- 官方直链失效时不退回未知镜像，也不声称应用不可获得；应显示“官方来源当前不可达”。
- 在无法取得 6.0.7 包体并核验摘要、包名和签名前，catalog 不能标记为可执行安装。

### 验收标准

1. 当贝市场普通流程不再要求用户自行提供 APK。
2. catalog 记录官方产品页、稳定版本、官方页解析的下载目标和允许主机。
3. 下载只接受官方允许主机，重定向到未知主机时失败关闭。
4. APK 经包名、版本、签名、大小和 SHA-256 校验后才可生成安装计划。
5. 本项目不在缺少再分发许可时镜像当贝市场 APK。
6. 官方链接失败时提供官方页和重试选项，不回退到未知第三方资源。
7. 四个平台使用同一个 resolver、catalog 记录、验证结果和问题选项。
