# Android TV Apps Helper：体验反馈持续记录

本文件用于持续收集真实 Agent 使用过程中暴露的问题。条目处于 `已收集` 状态时，仅代表问题和验收口径已经记录，不代表代码已修改或平台验证已完成。

## UX-001：问题组件内缺少上一轮结果、进度和解决指引

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 补充日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮用户提交的两张 WorkBuddy 截图。截图未作为仓库资源持久化。

### 观察到的问题

在设备发现阶段，WorkBuddy 展示了以下交互：

1. `S2-Q1` 首次未发现设备时，直接询问“接下来怎么做”，提供“重新扫描设备 / 提交电视 IP 地址 / 安全退出”。
2. `S2-Q1` 第三次仍未发现设备时，直接提供“扫描局域网查找电视 / 提交电视 IP 地址 / 再次扫描设备 / 安全退出”。

两轮都没有在问题之前说明：

- 上一轮执行了哪些发现方式，以及命令是否成功执行；
- 已重试多少次、发现了什么、排除了什么；
- 当前卡点是什么；
- 用户应如何在电视上开启 ADB，以及开启后如何继续。

这会让用户在相同选项之间反复尝试，却没有足够信息自行排除电视端设置问题。

补充观察：Agent 的普通对话上下文中可能已经包含上一轮情况，但弹出的选择组件会成为用户当前唯一的视觉焦点。上下文如果只出现在组件外的对话正文中，用户仍然很容易忽略它；因此这不是单纯的“上下文是否生成”问题，而是“关键上下文是否进入问题组件”问题。

### 期望行为

每一轮提问都必须先整理简短、可核对的上下文，并将其与唯一一个“问题 + 选项”共同放入当前交互组件或同一个连续的文字交互块中：

1. **上一轮结果**：做了什么检查、获得了什么结果；
2. **当前进度**：流程完成到哪一步、当前阻塞点是什么；
3. **处理指引**：用户现在可执行的具体解决步骤；
4. **本轮问题与选项**：优先使用平台原生选择组件，不支持时使用等价编号文字菜单。

首次提问没有“上一轮”时，也应明确写明“尚未执行设备检查”，并说明即将执行的检查范围。

对于弹窗、卡片、表单等原生选择组件，以上第 1 至第 3 项必须显示在组件内部，位于问题和选项之前。仅在组件外先发送一条普通对话消息，不视为满足要求。若平台的组件 API 只有“问题文本”和“选项”字段，应把压缩后的结果、进度和指引合并到问题文本中，而不是省略。

推荐的组件内信息顺序为：

```text
上一轮结果：第 3 次扫描完成，未发现 ADB 设备。
当前进度：电脑端检查已完成，正在等待电视开启网络调试并授权。
处理指引：设置 → 系统/关于本机 → 连点版本号约 7 次 → 开发者选项 → 开启 ADB/网络调试。

问题 S2-Q1：完成上述检查后，接下来怎么做？
[再次扫描设备] [提交电视 IP 地址] [查看完整指引] [安全退出]
```

### 未发现 ADB 设备时必须提供的文字指引

指引需使用用户可操作的语言，并提示不同品牌菜单名称可能不同：

1. 确认电视和运行 Agent 的电脑连接到同一个可信局域网；访客网络或开启了客户端隔离的 Wi-Fi 可能互相不可见。
2. 在电视中打开“设置”，进入“设备偏好设置 / 系统 / 关于本机”。
3. 连续点击“版本号 / Build”约 7 次，直到电视提示已开启开发者模式；部分电视会要求输入锁屏密码。
4. 返回“系统 / 开发者选项”，打开“USB 调试 / ADB 调试 / 网络调试 / 无线调试”中的对应开关。
5. 在“网络与互联网”或“关于本机”中查看电视 IP 地址。
6. Agent 发起连接后，在电视上核对并接受 RSA 调试授权提示；未授权、离线或仅端口可达都不能视为已连接。

如果平台支持图片展示，且能够获得与电视品牌、型号和系统版本匹配的可靠素材，可在文字步骤后附带标注截图或示意图。不得用不匹配的品牌界面冒充真实路径；缺少可靠截图时保留完整文字指引，并只在确有必要时用受约束选项询问品牌或系统类型。

### 跨平台内容对等要求

- 四个平台必须展示相同的结果摘要、进度、解决指引、问题 ID 和选项语义；仅允许因平台能力不同而改变展示形式。
- WorkBuddy、豆包工作若支持原生选择卡片，必须把摘要、进度和指引放入同一张卡片内部，并置于问题和选项之前；卡片外的普通对话正文不能替代卡片内上下文。
- Codex、Claude Desktop/Code 若无原生卡片，应输出等价的编号文字选项。
- 用户回答不明确、答非所问、使用旧问题的答案或输入格式错误时，不得推进状态或执行后续命令；应重新展示当前 `pending_question`，并保留更新后的结果摘要和处理指引。

### 待实现的数据字段建议

- `previous_result_summary`：上一轮执行与发现
- `progress_summary`：已完成步骤与当前阻塞
- `remediation_guidance`：与当前阻塞直接相关的解决步骤
- `evidence`：检查方式、次数和关键结果
- `visual_aid`：可选、来源可靠且与设备匹配的截图或示意图
- `component_context`：由上述字段压缩生成、必须随 `pending_question` 一同渲染的组件内上下文

### 验收标准

1. 每个交互回合的问题组件内部，在问题和选项之前包含“上一轮结果、当前进度、处理指引”；首次回合明确尚未检查。只在组件外显示不算通过。
2. `S2` 零设备结果显示本轮实际采用的发现方式、执行结果和累计尝试次数。
3. 首次未发现设备时即提供简要 ADB 开启检查；重复未发现时展示完整的电视端 ADB 开启与授权指引，再给出选项。
4. 所有截图或示意图都有可靠来源且与目标设备场景相符；无法确认时不伪造截图。
5. Claude Desktop/Code、Codex、WorkBuddy、豆包工作的信息内容对等，只有 UI 载体可以不同。
6. 无效回答只重显当前问题，不改变流程状态，也不触发下一步命令。
7. 未经用户明确选择和范围确认，不扩大到局域网扫描；选择扫描时先说明扫描范围和用途。

### 后续实现分组

- 扩展统一对话响应结构与渲染器；
- 为原生组件增加上下文内嵌适配，并为字段受限的平台提供问题文本合成降级；
- 补全 `S2` 无设备分支的分级排障文案；
- 增加可选视觉指引能力及素材可信度约束；
- 为四平台包补充内容对等和状态不前进测试；
- 分别在四个平台复测首次未发现、重复未发现、无效回答和恢复成功场景。

## UX-002：用户界面暴露过长且不可理解的内部方案 ID

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮用户截图中的 `PLAN-a239e10cdfa2` 同时出现在方案标题和确认问题中。截图未作为仓库资源持久化。

### 观察到的问题

`PLAN-a239e10cdfa2` 是适合机器校验和审计的内部标识，但长度较长、含义不直观。将其作为主要方案名称展示，会迫使非技术用户理解无意义的字母和数字，也会让不同模型自行缩写或改写名称。

### 固定命名规则

Skill 必须区分“内部不可变 ID”和“用户可见名称”，两者不得混用：

- 内部不可变 ID：继续使用 harness 生成的 `PLAN-<digest>`，用于计划完整性校验、日志、恢复和防止旧授权复用；不得由模型生成或修改。
- 用户可见名称：由渲染器按照固定模板生成，不允许模型自由命名。
- 固定模板：`方案 {两位会话序号}：{固定动作名称}`，例如 `方案 01：安装应用`。
- 允许在需要区分电视时扩展为：`方案 01：为客厅电视安装应用`；设备没有可信友好名称时使用“电视”，不把 IP、serial 或摘要哈希拼入主标题。
- 固定动作名称只能从枚举映射取得，例如 `安装应用`、`设置默认桌面`、`诊断应用`，不得由模型生成同义词。

内部 ID 可在“技术详情 / 诊断信息”中按需展开，但普通确认问题应写成“是否执行方案 01：安装应用？”，不能直接询问是否执行一串哈希 ID。

### 验收标准

1. 四个平台的普通用户界面和问题组件都使用相同的固定用户可见名称。
2. 同一会话中的方案序号从 `01` 递增，重复渲染同一方案时序号不变。
3. 模型不能创建、缩写、翻译或重写方案名称；名称只能由统一渲染器生成。
4. 内部 `PLAN-<digest>` 仍绑定设备、应用、动作和文件摘要，用户可见名称的简化不得削弱原有安全校验。
5. IP、ADB serial 和摘要哈希默认不进入方案标题；需要排障时只在技术详情中显示。

## UX-003：功能入口“电视清理”和“推荐配置”语义不清

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

### 观察到的问题

“电视清理”没有说明要清理什么，容易被理解为清理缓存、卸载应用、恢复出厂设置或修改桌面。“推荐配置”也没有说明它会展示应用、下载应用还是直接安装应用。

### 固定入口名称与说明

四个平台统一采用以下名称，不允许模型自行换同义词：

| 原名称 | 固定显示名称 | 组件内说明 |
| --- | --- | --- |
| 电视清理 | 设置电视默认桌面 | 查看当前桌面应用，并选择要设为默认桌面的应用；执行前另行确认。 |
| 推荐配置 | 查看并选择推荐应用 | 查看可用应用清单，选择需要下载的应用；选择后按应用名称二次确认。 |

“设置电视默认桌面”只能进入桌面相关流程，不能暗中扩大为卸载应用、删除数据、清理缓存或恢复出厂设置。“查看并选择推荐应用”不能在用户完成选择和二次确认前开始下载或安装。

### 验收标准

1. 四个平台使用完全一致的入口名称和组件内说明。
2. 每个名称准确描述紧接着发生的动作，不使用“清理”“配置”等无对象的概括词。
3. 选择入口本身不触发下载、安装、卸载、清除数据或更改默认桌面。
4. 旧名称仅可在版本迁移说明中出现，不能继续作为交互选项。

## UX-004：推荐应用缺少列表选择和按名称二次确认

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

### 观察到的问题

截图中的流程直接生成了包含 8 个应用、但“可执行安装项为 0 项”的计划，然后询问是否执行。应用表格在此处承担的是计划结果展示，而不是让用户选择要下载的应用；用户缺少一个明确的候选列表选择步骤，也没有看到按应用名称确认下载范围的独立问题。

### 期望流程

进入“查看并选择推荐应用”后，必须先展示当前可供用户选择的应用列表。每一项至少包含稳定编号、应用名称、版本和当前状态，例如“未安装 / 可更新 / 已是最新版本 / 暂不可下载”。没有合法下载源或处于 `pending_rights` 的应用应明确标注且不可选。

选择方式按平台能力固定降级：

1. 平台交互组件支持多选时，直接在同一个组件中提供应用多选列表。
2. 不支持多选时，展示带编号的完整列表，并要求用户用数字和顿号输入，例如 `1、2、3、4`。
3. 文字解析器至少兼容中文顿号 `、`、中文逗号 `，`、英文逗号 `,` 和空格，但界面示例统一使用顿号，避免不同模型自行规定格式。
4. 遇到不存在的编号、重复编号、不可下载项或无法解析的输入时，说明具体错误并重新显示同一个选择问题；不得进入下载或安装。

无论采用组件多选还是数字输入，完成初选后都必须新增一个独立的二次确认问题。确认组件必须把编号解析为应用名称，并完整列出将要下载的应用，例如：

```text
上一轮结果：已选择 4 个应用。
准备下载：软件 A、软件 B、软件 C、软件 D。
当前进度：尚未开始下载，也没有对电视执行安装操作。

问题：是否确认下载以上 4 个应用？
[确认下载] [返回修改选择] [安全退出]
```

确认时不能只显示 `1、2、3、4`、内部包名或方案 ID。用户选择“返回修改选择”后回到同一份应用列表，保留或清楚标示原选择；只有选择“确认下载”后才能开始下载。下载和校验完成后，如需安装到电视，仍必须进入独立的安装计划与执行批准流程。

### 状态约束

- `APP_SELECTION`：展示列表并收集多选或数字输入，不产生下载副作用。
- `DOWNLOAD_CONFIRMATION`：按名称展示解析后的选择，等待明确确认。
- `DOWNLOAD_AND_VERIFY`：仅在确认后下载，并逐个显示来源、版本和 SHA-256 校验结果。
- `INSTALL_PLAN`：下载成功不等于批准安装；安装仍绑定设备、文件摘要、动作和内部计划 ID。

### 验收标准

1. 所有可选应用先以列表展示，平台支持时使用真正的多选组件。
2. 文本降级模式接受 `1、2、3、4`，并按固定规则解析，不依赖模型临场理解。
3. 初选不会触发下载；必须经过独立的二次确认。
4. 二次确认逐项显示用户能理解的应用名称和版本，而不是只显示数字、包名或内部 ID。
5. 用户修改选择或输入无效时，不丢失上下文、不推进状态、不产生副作用。
6. 下载确认与安装确认相互独立，确认下载不能被解释为同时批准安装。
7. 四个平台的候选列表、解析结果、确认内容和状态流转保持对等。

## UX-005：Emotn UI 安装后缺少默认桌面与壁纸设置流程

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮用户截图中的 `S7-Q2` 仅提供“启动 Emotn UI 并验收前台，且不改任何默认设置”，没有继续提供设置默认桌面和壁纸的受控选项。截图未作为仓库资源持久化。

### 观察到的问题

当前桌面流程把“安装或启动 Emotn UI”当作终点，但用户的实际目标还包括：

1. 在明确授权后把 Emotn UI 设置为电视默认桌面；
2. 安装完成后选择上传一张图片作为电视壁纸，或明确继续使用默认壁纸；
3. 在作出壁纸选择时再次看到“自定义壁纸可能被电视系统重置”的限制提示。

### 固定风险提示

凡是询问是否设置、替换或重新应用壁纸，问题组件内部都必须原样表达以下含义，不得只放在组件外的对话正文中，也不得被模型省略或改写成永久有效的承诺：

> 提醒：自定义壁纸可能被不同品牌的电视系统在几天后自动恢复为系统默认壁纸；电视重启、系统更新或桌面更新后也可能发生重置。本 Skill 无法保证壁纸永久保留。

如果壁纸问题因图片缺失、格式无效、传输失败或设置失败而重显，这条提示也必须随当前 `pending_question` 一起再次显示。

### 固定后续流程

Emotn UI 安装和基础启动验证通过后，必须按以下顺序继续，不允许模型跳步或合并授权：

1. `DEFAULT_LAUNCHER_CHOICE`：询问是否把 Emotn UI 设置为默认桌面。
2. `DEFAULT_LAUNCHER_APPLY`：仅在用户明确确认后执行设置，并展示实际结果；不得卸载、禁用或清除电视原厂桌面数据。
3. `WALLPAPER_CHOICE`：在组件内显示固定风险提示，再询问使用自定义图片还是默认壁纸。
4. `WALLPAPER_UPLOAD`：选择自定义图片后，要求用户上传一张图片；图片未提交或无效时保持在当前问题，不得静默改用其他文件。
5. `WALLPAPER_APPLY`：展示即将使用的图片和目标电视，获得明确确认后才传输和设置。
6. `WALLPAPER_VERIFY`：显示命令或系统返回结果，并请用户在电视上确认画面；仅有命令成功不能声称壁纸视觉验收通过。

默认桌面问题使用固定选项：

```text
上一轮结果：Emotn UI 已安装并完成基础启动检查。
当前进度：尚未更改电视的默认桌面；原厂桌面会保留。

问题：是否把 Emotn UI 设置为默认桌面？
[设为默认桌面] [只使用 Emotn UI，不改默认桌面] [返回上一步] [安全退出]
```

壁纸问题使用固定选项：

```text
上一轮结果：Emotn UI 的桌面设置步骤已完成。
当前进度：尚未修改电视壁纸。
提醒：自定义壁纸可能被不同品牌的电视系统在几天后自动恢复为系统默认壁纸；电视重启、系统更新或桌面更新后也可能发生重置。本 Skill 无法保证壁纸永久保留。

问题：要使用哪一种壁纸？
[上传一张图片作为壁纸] [使用默认壁纸] [返回上一步] [安全退出]
```

选择“上传一张图片作为壁纸”后，下一轮必须明确要求上传一张图片。选择“使用默认壁纸”或明确不上传时，保留 Emotn UI 的默认壁纸，不执行自定义壁纸命令。不能把用户未回复、附件上传失败或图片格式无效自动解释为选择默认壁纸。

### 验收标准

1. Emotn UI 安装完成后，流程不会直接结束，而是依次处理默认桌面选择和壁纸选择。

4. 每次显示壁纸相关问题时，风险提示都位于同一个问题组件内部。
5. 用户可明确选择“上传一张图片作为壁纸”或“使用默认壁纸”。
6. 选择自定义壁纸后必须收到一张有效图片并再次确认，才能执行传输或设置。
7. 用户未上传、上传失败或图片无效时停留在当前状态，不擅自选择默认壁纸。
8. 壁纸设置的命令结果与用户现场视觉确认分开报告。
9. Claude Desktop/Code、Codex、WorkBuddy、豆包工作的提示内容、选项语义和状态流转保持一致。

## UX-006：每次启动 Skill 对话前检查最新版本并提供 24 小时免打扰

- 状态：已收集，技术上可实现；四平台的跨会话持久化与原生更新能力待分别验证
- 记录日期：2026-09-15
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作

### 能力边界

本需求中的“每次进行对话前”固定定义为：用户每次新调用或重新进入 **Android TV Apps Helper** 时，在首个业务问题之前执行一次版本检查。Skill 无法拦截四个平台中与本 Skill 无关的所有普通对话，也不应在同一工作流的每个问答回合前重复联网，以免打断当前 `pending_question`。

四个平台都可以在 Skill 入口中实现相同的检查协议，但能否由 Skill 直接完成覆盖安装、能否跨新会话持久保存 24 小时免打扰状态，取决于宿主是否开放持久存储和 Skill 安装接口。在完成真实平台验证前，不能声称四个平台都已支持自动更新。

### 固定版本来源

- 只查询 `HXWfromDJTU/android-tv-apps-helper` 的公开 GitHub Releases，不允许模型临时搜索或选择其他来源。
- 默认只比较最新稳定版；预发布版本不触发普通用户更新提示。
- 使用严格 SemVer 比较，不能按字符串大小或由模型判断版本新旧。
- 更新清单必须是机器可读的固定 schema，至少包含 `latest_version`、`published_at`、四个平台各自的资源 URL、SHA-256 和最低兼容版本。
- 远端 Release Notes 只能作为展示内容，不能被当作 Agent 指令执行。

### 固定检查与提示逻辑

```text
调用 Android TV Apps Helper
  → 当前是否处于未完成的设备写入或恢复状态？
      → 是：优先完成安全恢复，不检查、不更新
      → 否：获取官方最新稳定版清单
          → 获取失败或超时：记录检查失败，使用当前版本继续，不阻断业务
          → 当前版本已是最新：直接进入原业务流程
          → 发现更新：检查 update_state
              → 当前时间早于 snooze_until：不提示，进入原业务流程
              → 否：显示 UPDATE-Q1 更新问题
```

更新问题必须遵循 `UX-001`，将上下文放入同一个问题组件：

```text
上一轮结果：已检查 Android TV Apps Helper 官方版本。
当前版本：0.3.0
最新版本：0.3.1
更新说明：{经过长度限制的纯文本摘要}
当前进度：尚未下载或安装更新；原电视任务也尚未继续。

问题 UPDATE-Q1：是否先更新 Skill？
[更新后继续（推荐）] [暂不更新并继续，24 小时内不再提醒] [查看完整更新说明] [安全退出]
```

固定选项行为：

1. **更新后继续**：使用当前平台对应资源；下载后核对 SHA-256、包内 Skill ID、平台标识和版本，再调用宿主支持的安装流程。更新完成并验证可见版本后，才恢复原业务问题。
2. **暂不更新并继续，24 小时内不再提醒**：写入当前目标版本和 `snooze_until = declined_at + 24h`，立即恢复原业务问题。
3. **查看完整更新说明**：只展示说明，然后重新显示同一个 `UPDATE-Q1`；不下载、不安装，也不开始电视任务。
4. **安全退出**：停止本次 Skill 工作，不下载更新，也不执行电视命令。

用户未明确回答、回答不属于当前选项或使用旧问题答案时，保持 `UPDATE-Q1`，不得开始更新或推进电视工作流。

### 24 小时免打扰状态

宿主适配器应以原子方式持久化以下字段：

- `installed_version`
- `latest_seen_version`
- `declined_version`
- `declined_at`
- `snooze_until`
- `last_check_at`
- `last_check_result`

免打扰按“用户 + 平台 + Skill + 被拒绝的目标版本”记录。用户拒绝后 24 小时内仍可执行只读版本检查，但不得再次弹出更新问题。满 24 小时后，如果当前版本仍落后，则在下一次调用 Skill 时再次提示。

如果宿主没有跨会话持久存储能力，只能做到当前会话免打扰，不能假装已经满足 24 小时规则；该平台应标记为兼容性阻塞，直到提供可靠存储适配。

### 更新安全约束

- 永不静默自动更新；必须由用户选择“更新后继续”。
- 版本检查是只读网络请求；更新下载和安装是独立的、用户明确批准的动作。
- 下载失败、摘要不符、平台包不匹配、安装失败或新版本不可见时，保留当前可用版本并显示失败原因。
- 更新过程中不得执行 ADB 写操作；如有未完成的安装计划，更新后必须重新校验会话 schema、目标设备、APK 摘要和计划有效性。
- Skill 包不能仅凭自己输出“更新完成”；必须读取宿主实际可见的已安装版本作为证据。
- GitHub 不可达时使用当前已安装版本继续，不把网络失败误报为“已经是最新版”。

### 跨平台降级

1. 宿主支持由 Agent 安装 Skill：用户确认后走宿主原生安装，并验证版本。
2. 宿主只支持上传 ZIP 或人工安装：用户确认后提供唯一对应平台的资源、SHA-256 和固定安装步骤；安装前暂停电视任务，安装完成后重新调用并验证。
3. 宿主不允许 Skill 联网：显示“本平台无法自动检查版本”，可提供固定的手动检查入口，但不伪造检查结果。
4. 宿主不提供跨会话持久化：明确标为不满足 24 小时免打扰，不能降级成每次都重复提示。

### 验收标准

1. 每次新调用或重新进入本 Skill 时，在首个业务问题之前恰好执行一次版本检查；同一连续工作流中不逐轮重复检查。
2. 发现新稳定版时，更新问题和版本上下文位于同一个交互组件内。
3. 用户拒绝的目标版本在接下来 24 小时内不再次弹窗；24 小时后仍落后才重新提示。
4. “查看说明”、无效回答和网络失败都不会触发下载、安装或 ADB 命令。
5. 未经明确确认不更新；确认更新也只使用当前平台匹配且校验通过的官方资源。
6. 更新完成、失败、当前已是最新和无法检查四种结果必须分别展示，不能混用。
7. 若入口时存在未完成的设备写入或恢复状态，安全恢复优先于版本检查。
8. Codex、Claude Desktop/Code、WorkBuddy、豆包工作分别验证：联网检查、版本比较、拒绝后跨会话 24 小时免打扰、确认更新、失败回滚和原问题恢复。

## UX-007：首次问题前应自动完成只读预检查并在组件内展示结果

- 状态：已收集，待统一设计与实现
- 记录日期：2026-09-15
- 观察平台：腾讯 WorkBuddy（中国大陆版）
- 适用范围：Claude Desktop/Code、Codex、腾讯 WorkBuddy、豆包工作
- 证据：本轮截图中的首屏仍在询问“是否开始只读预检”，要求用户先选择“开始只读预检 / 查看范围 / 安全退出”，尚未提供任何实际检查结果。截图未作为仓库资源持久化。

### 观察到的问题

安全的只读预检查本身不需要用户先批准。把“是否开始预检”作为首次问题，会增加一个无法帮助用户作出业务选择的回合，也违背“问题组件应承载当前事实和阻塞点”的要求。

首次有意义的问题应建立在已经执行完成的预检查结果上，而不是询问是否开始检查。组件要让非技术用户直接看懂：电脑端是否具备条件、当前网络发现了什么设备、其中哪些可能是电视、是否已经存在已授权的 ADB 连接，以及接下来需要用户确认什么。

### 固定启动顺序

```text
调用 Android TV Apps Helper
  → 处理未完成的设备写入或安全恢复（如有）
  → 执行 UX-006 版本检查（到达安全检查点时）
  → 自动执行安全、只读、有限范围的 PRECHECK
  → 生成结构化检查结果
  → 在首次问题组件内展示结果、确认事项和操作指引
  → 等待用户明确回答当前问题
```

旧的 `S0-Q1：是否开始只读预检？` 应取消。预检查成功、部分成功或失败都必须先产生明确结果，再进入对应的首次问题；不能因为某一项不可用而只抛出空白选择。

### 自动预检查的固定范围

无需再次征求同意即可执行的只读项目：

1. 检查当前 Agent 是否运行在能够访问本机网络和 ADB 的执行环境。
2. 检查 ADB 是否已安装、可执行，并记录版本或具体错误。
3. 执行 `adb devices -l`，列出已经被 ADB 发现的设备及 `device / unauthorized / offline` 状态。
4. 读取电脑当前活动网络接口和本机地址；在宿主允许且不会暴露敏感凭据时，显示当前 Wi-Fi 名称。
5. 读取本机已有的邻居缓存、ADB 已知目标和被动 mDNS/服务发现结果，整理“可能的电视设备”。

自动预检查不得主动扫描整个子网、探测所有 IP 或尝试连接未经用户选择的地址。需要主动局域网扫描时，必须另设问题，说明扫描的网段、端口、用途和范围，得到明确选择后才能执行。

### 检查结果的固定展示结构

首次问题组件必须至少显示：

| 项目 | 固定结果类型 | 用户可见示例 |
| --- | --- | --- |
| 执行环境 | 可访问本机 / 仅云端 / 无法判断 | 当前在本机运行，可以检查电视连接。 |
| ADB 工具 | 可用 / 不可用 / 检查失败 | ADB 已安装，版本 1.0.41。 |
| 当前网络 | 已连接 / 未连接 / 无法读取 | 电脑已连接 Wi-Fi“家庭网络”。 |
| 已发现设备 | 数量与状态 | 发现 2 个网络设备，其中 1 个可能是电视。 |
| ADB 电视 | 已授权 / 未授权 / 离线 / 未发现 | 未发现已授权的 ADB 电视。 |
| 检查范围 | 被动、有限范围 | 未主动扫描整个局域网，也未向电视发送修改命令。 |

不得把邻居缓存中的普通设备直接断言为电视。识别依据不足时使用“可能是电视 / 未能确认设备类型”，并显示名称、IP 或发现方式等可核对信息。未发现设备也不能断言电视没有开启 ADB，只能说明当前检查没有发现可用连接。

### 首次确认问题

预检查结果后，依次确认“是否同一 Wi-Fi”和“是否已开启 ADB”。仍需遵守每轮只提出一个问题的约束，不把两个独立确认塞进一个含糊的是非题。

首个问题组件示例：

```text
预检查结果：
- 电脑已连接 Wi-Fi“家庭网络”。
- ADB 工具可用。
- 被动发现 2 个网络设备，其中 1 个可能是电视：客厅电视（192.168.31.157）。
- 尚未发现已授权的 ADB 连接。
- 本轮未主动扫描整个局域网，也没有修改电视。

当前阻塞：需要先确认电脑和电视是否接入同一个 Wi-Fi。

问题 PRECHECK-Q1：电脑和电视目前是否连接到同一个 Wi-Fi？
[是，同一个 Wi-Fi] [不是] [不确定，查看检查方法] [安全退出]
```

确认处于同一 Wi-Fi 后，再显示 ADB 问题：

```text
上一轮结果：你已确认电脑和电视连接到同一个 Wi-Fi。
当前进度：网络条件已确认；尚未发现已授权的 ADB 连接。

开启 ADB：电视设置 → 系统/设备偏好设置 → 关于本机 → 连续点击版本号约 7 次 → 返回开发者选项 → 开启 ADB/网络调试。随后接受电视上的 RSA 授权提示。

问题 PRECHECK-Q2：电视目前是否已开启 ADB 或网络调试？
[已开启，重新检查] [尚未开启] [不确定，查看完整指引] [安全退出]
```

### 指引载体

- 问题组件中始终保留足以完成操作的简要文字步骤，不能只给外部链接。
- 可同时提供项目内固定文档链接，文档需公开可访问、与当前 Skill 版本对应，并包含不同电视系统的菜单差异说明。
- 宿主支持图片时，可在同一组件或紧邻组件的位置展示可靠的步骤示意图；图片必须标明适用品牌或“通用示意”，不能伪装成用户电视的真实界面。
- 如果品牌差异导致通用步骤无法继续，应使用受约束选项询问品牌或系统类型，再展示匹配指引，不要求用户自由描述一大段设备信息。

### 失败与降级

- ADB 不可用：显示具体缺失项和安装/修复指引，然后询问“完成后重试 / 查看完整安装指引 / 安全退出”。
- 宿主仅能在云端运行：明确说明无法检查用户局域网，优先引导切换到本机执行环境，不生成虚假的设备列表。
- 无法读取 Wi-Fi 名称：显示“无法读取”，通过问题请用户人工确认，不把未知写成已连接。
- 未发现设备：显示已执行的检查、当前限制和 ADB 开启步骤，再提供重新检查、提交电视 IP、申请有限范围扫描或安全退出。

### 验收标准

1. 启动 Skill 后不再出现“是否开始只读预检”的空前置问题。
2. 首次有意义的问题之前已自动执行预检查，并在同一个组件内展示真实结果。
3. 结果明确区分已确认电视、可能是电视、普通设备和无法识别，不夸大探测能力。
4. 预检查只使用固定的被动或有限范围方法；主动局域网扫描仍需明确范围授权。
5. 同一 Wi-Fi 与 ADB 开启状态分两轮确认，每轮只有一个问题和固定选项。
6. ADB 指引至少包含可直接执行的文字步骤；链接或图片是增强项，不替代文字。
7. 检查失败、云端环境和权限不足都有清楚的结果与恢复选项，不展示虚假成功。
8. Claude Desktop/Code、Codex、WorkBuddy、豆包工作的预检查字段、问题顺序和降级语义保持一致。
